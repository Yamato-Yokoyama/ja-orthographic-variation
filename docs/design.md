# 設計

## 1. 問いと仮説

**問い（仮）**：日本語の表記ゆれを種類別に分けたとき、多言語の埋め込み検索の精度は、どの種類でどれだけ落ちるか。英語の書き方違いと比べてどうか。

仮説（実験で確かめる。外れても結果として書く）
- H1. 埋め込みモデルでも、書き方を変えるだけで nDCG@10 が落ちる。落ち方はゆれの種類で大きく違う
- H2. 文字の種類が変わるゆれ（漢字→ひらがな、英字→カタカナ）は、同じ文字の種類の中のゆれ（送り仮名、長音の有無）より大きく落ちる
- H3. 日本語の書き方違いによる低下は、英語の書き方違いによる低下より大きい
- H4. 単語一致の BM25 は埋め込みより大きく落ちる。ただし NFKC 正規化で直る種類（全角半角）では差が消える

問いは T0 で本人と一行に固める（open-questions Q2）。

## 2. 対象と対象外

| 区分 | 中身 | 理由 |
|---|---|---|
| 対象 | 同じ語の書き方だけが違うもの（どれも正しい書き方） | 先行研究の空き（related-work.md） |
| 対象外 | 同義語への置き換え（「不具合→バグ」） | 別の語になる。言語処理学会 2025 が扱った |
| 対象外 | 誤字（「イヤホン→イヤホヌ」） | 間違い。英語では EMNLP 2021 以降の研究が多い |
| 対象外 | 文字化け（Shift-JIS と UTF-8 の取り違え） | データ処理のバグで、言語の問題ではない |
| 対象外（後で） | 音声入力の誤変換、言語識別の誤り | 表記ゆれの上流で起きる別の問題 |

## 3. ゆれの種類（候補。最終的な一覧は Q4 で決める）

| ID | 種類 | 日本語の例 | 書き換えの作り方の候補 |
|---|---|---|---|
| `kanji_kana` | 漢字 → ひらがな | 取扱 → とりあつかい | 形態素解析の読み（SudachiPy）を使う |
| `okurigana` | 送り仮名 | 取扱い → 取り扱い | Sudachi の正規化形・辞書、手作業 |
| `katakana_var` | カタカナの揺れ | コンピュータ → コンピューター、バイオリン → ヴァイオリン | 長音の付け外しの規則、手作業 |
| `latin_katakana` | 英字 ↔ カタカナ | iPhone → アイフォン | 対応表（手作業か LLM＋人の確認） |
| `hira_kata` | ひらがな ↔ カタカナ | ねこ → ネコ | 規則（jaconv など） |
| `width` | 全角 ↔ 半角 | ＡＩ → AI、カメラ → ｶﾒﾗ | 規則（jaconv、NFKC の逆） |
| `itaiji` | 異体字 | 竜 → 龍 | 異体字の対応表（件数が少なければ外す） |
| `identity` | 書き換えなし（対照） | そのまま | 元クエリをそのまま使う。低下率が 0 になることを確かめる |

英語の比較用（ESCI の us）
| ID | 種類 | 例 |
|---|---|---|
| `en_hyphen` | ハイフン・スペース | e-mail → email、t shirt → t-shirt |
| `en_case` | 大文字小文字 | iPhone → IPHONE |
| `en_spelling` | 英米の綴り | color → colour |

決まりごと
- 1つの変形クエリでは**1種類のゆれだけ**を入れる（種類ごとの影響を分けるため）
- そのゆれを入れられないクエリは、その種類の対象から外す（件数は種類ごとに違ってよい。件数を必ず表に出す）
- 書き換えは**意味を変えない**。ESCI の関連度ラベルは元クエリのものをそのまま使うので、ここが崩れると結果が無効になる → 種類ごとに 50 件を本人が目で確認する（Q5）

## 4. データ

- 元クエリ：Amazon Shopping Queries Dataset（ESCI）の日本語、Task 1 の test（3,123 クエリ、88,789 判定。ML塾の README の数字。T2 で確かめる）。ライセンス Apache-2.0
- 英語の比較：ESCI の us の test から同じ規模を抜き出す（件数は Q3）
- 追加の候補：JMTEB の検索タスク（言語処理学会 2025 と同じ JAQKET・JaGovFaqs-22k）。先行研究と直接比べられる（Q3）
- ESCI を選ぶ理由：実際に Amazon で打たれたクエリなので「現場で起きる問題」と言える。人が付けた正解ラベルがある。ML塾ですでに読み込みと nDCG の仕組みがある

## 5. モデル

| 区分 | 候補 | 役割 |
|---|---|---|
| 単語一致 | BM25（文字 bigram）、BM25（Sudachi の形態素） | 対照。埋め込みと比べる |
| 多言語埋め込み | bge-m3、multilingual-e5-base / large | 本命。言語処理学会 2025 と SIGIR 2025 と重なる |
| 日本語特化の埋め込み | ruri-base / large | 日本語で学習したモデルは強いのか |
| LLM ベースの埋め込み | （Q6。Mac で動く大きさのものがあれば） | 先行研究3本が扱っていない |
| 安い直し方 | NFKC 正規化してから検索 | 「正規化だけでどこまで直るか」の基準 |

モデルは Q6 で最終的に決める。最初は BM25 と bge-m3 の2つだけで T4 まで通す。

## 6. 測り方

- 主指標：重み付き nDCG@10（E=1.0, S=0.1, C=0.01, I=0。KDD Cup 2022 Task 1 と同じ。ML塾と同じ）
- 低下率：(元クエリの nDCG − 変形クエリの nDCG) ÷ 元クエリの nDCG を、種類 × モデルごとに平均
- 差の信頼区間：クエリ単位の paired bootstrap（1,000 回）で 95% 区間を出す
- 先行研究と比べるための補助指標：Top-5 の「前後とも正解」「片方だけ正解」の件数（言語処理学会 2025 の AND / XOR と同じ形）
- クエリ単位の失敗例：低下が大きかったクエリの上位 20 件を、元と変形で並べて `results/` に残す（レポートの例に使う）

計算の工夫：書き換えるのはクエリだけなので、**商品側の埋め込みは一度だけ計算してキャッシュする**。変形クエリの埋め込みだけを毎回計算する。

## 7. ML塾（jp-product-search-eval）との関係

- ML塾には、ESCI の読み込み（`esci_eval/data.py`）、nDCG（`metrics.py`）、BM25（`bm25.py`）、bge-m3（`dense.py`）がある（または作っている途中）
- この研究はそれを**使う側**。同じものを二度書かない
- 使い方（import する／コピーする／共通部分を切り出す）は Q7 で決める
- ML塾は「否定・比較・数量」、この研究は「表記ゆれ」と、見る言語現象が違う。重ならないように README に書き分ける

## 8. 応募までにやること・やらないこと

| やる（応募まで） | やらない（応募の後） |
|---|---|
| 種類別の低下率の表、失敗例、2ページのレポート、再現できるリポジトリ | 表記ゆれを混ぜた fine-tuning、リランカーでの直し、LLM によるクエリの書き直し |

「測る」まででも、先行研究の空きを埋める結果になる。「直す」は面接や卒論で「次にやること」として話す。
